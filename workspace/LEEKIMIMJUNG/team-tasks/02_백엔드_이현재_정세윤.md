# 백엔드 담당 — 이현재, 정세윤

## 1. 시작하기 전에 알아야 할 것

### 기본 지식
- TS/JS 기초 문법 (변수, 함수, `async/await`, `filter`/`map`/`find` 같은 배열 메서드)
- REST API 호출 기초 (`fetch`, POST/GET, JSON body 주고받기) — Simulation API 연동에 필요
- **비동기 폴링 패턴** — Simulation API 연동은 한 번 호출하고 끝이 아니라 **세션생성→제출→검증→(될 때까지 상태 확인)→Evidence 조회** 순서로 이어짐. `while` 반복문 안에서 `await`로 상태를 반복 확인하는 패턴을 알아야 함 (예: `while (status === "PENDING") { await sleep(1000); status = await checkStatus(); }`)
- 타입은 직접 설계하지 않습니다. `UserProfile`, `SessionContext`, `Candidate` 등 모든 타입은 `@kiobridge/participant-sdk`가 이미 정의해뒀고, 우리는 그 모양대로 값만 채우면 됩니다.

### 이 프로젝트만의 핵심 개념 (반드시 이해하고 시작)
- **Profile vs SessionContext 구분**
  - `Profile` = 오래 유지되는 정보 (접근성 설정, 언어, 선호 입력방식)
  - `SessionContext` = 이번 방문에만 해당하는 정보, 그 안에서도 4개 섹션을 **절대 혼동 금지**:
    | 섹션 | 의미 | 불일치 시 |
    |---|---|---|
    | `facts` | 확인된 사실 (visitType, appointmentStatus, departmentId) | 차단 |
    | `preferences` | 선호 (supportModes) | 경고만 |
    | `hardConstraints` | 절대 조건 (medicalInferenceAllowed) | 차단 |
    | `capabilities` | 쓸 수 있는 수단 (canUseSelfCheckIn) | 양보 불가 |
  - 섹션을 섞으면 `DOMAIN_CONTEXT_MISMATCH` 오류로 거부됩니다.
- **공식 enum만 사용** — 값 표기는 enum `UPPER_SNAKE_CASE`, JSON 필드는 `camelCase`. 목록에 없는 값은 `UNKNOWN`이나 `extensions`에 넣기.
- **타임스탬프는 무조건 UTC ISO 8601** (`2026-08-03T00:11:00Z`) — SDK의 `nowIso8601Utc()` 사용, 로컬시각/`+09:00` 절대 금지.
- **fixture 개념** — 서버(`GET /api/v1/environments/hospital/fixture`)가 candidates(후보 6개)/optionGroups/transitions(화면 전환 규칙)를 이미 제공합니다. 우리는 이 데이터를 그대로 참고해서 채우는 것이지, 직접 설계하는 게 아닙니다.

### 예외 — `participant.ts`를 직접 건드려야 하는 작업이 하나 있음
다른 STEP들은 각자 자기 파일(`backend/`, `agent/`, `frontend/` 안)만 건드리면 되는데, **"UNKNOWN 상태·수동개입 발생 시 STOP 처리 로직"만은 다릅니다.** 이 로직은 `createSessionContext()`와 `recommend()` 사이, 즉 `participant.ts`의 `buildSubmission()` 함수 안에 직접 끼워 넣어야 동작해서, `participant.ts` 자체를 수정하게 됩니다.
- `participant.ts`는 다른 사람들도 보는 "재수출 허브"라 이 작업 할 때만 예외적으로 손댄다는 걸 팀에 미리 공유하고, 동시에 건드리는 사람이 없는지 확인 후 진행하세요.

### 우리가 절대 안 만들어도 되는 것 (플랫폼이 이미 제공)
- 시뮬레이터 자체, 상태머신, 별도 스키마 설계, 프로필 저장용 DB CRUD API — `packages/`, `apps/`, `environments/`, `schemas/`는 손대지 않습니다.

## 2. 시작 순서

### 0단계 — 환경 점검 (같이, 5분)
```bash
npm install
npm run participant:doctor
curl http://localhost:4000/api/v1/environments/hospital/fixture | less   # fixture 구조 눈으로 확인
```

### 1단계 — STEP 2 `mapToCanonicalInput()` / STEP 3 `createSessionContext()` (둘이 나눠서 병렬 시작)
프론트팀이 만드는 `collectProfile()` 출력을 기다릴 필요 없음 — 타입만 맞으면 되니 임시 mock 데이터로 먼저 시작 가능.

- **`mapToCanonicalInput()`**: `RawUserInput` → 공식 `UserProfile`. `language: "ko-KR"` 필수, `collectedAt`은 `nowIso8601Utc()`.
- **`createSessionContext()`**: `facts`/`preferences`/`hardConstraints`/`capabilities` 섹션 구성. Hard Constraint가 `UNKNOWN`이면 임의 추론 금지.

완료 확인: `npm run participant:progress -- --team LEEKIMIMJUNG`

### 2단계 — UNKNOWN 상태·수동개입 발생 시 STOP 처리 로직
STEP 3 직후, AI팀의 `recommend()` 호출 **직전**에 끼워 넣는 게이트 로직입니다. STEP 3 하던 사람이 이어서 진행하면 자연스럽습니다. (위 "예외" 참고 — 이 작업은 `participant.ts`를 직접 수정합니다)

1. `hardConstraints` UNKNOWN 값 검사 유틸 구현
2. UNKNOWN 시 재확인/직원도움/STOP 분기 로직 구현
3. 저신뢰 입력(`confidence<0.6`, `confirmedByUser=false`) 재확인 플래그 로직 구현
4. `recommend()` 호출 전 STOP 게이트 연결 구현
5. STOP 발생 사유 기록 로직 구현

### 3단계 — STEP 9 `buildExecutionPlan()`
AI팀의 `recommend()` 결과 타입(`Recommendation`)만 정해지면 실제 구현 완료를 기다리지 않고 mock으로 시작 가능. **가장 규칙이 많은 함수라 시간 넉넉히 잡기.**

1. 사용자 승인 후에만 실행계획 생성되도록 강제 로직 구현
2. fixture transitions 기반 액션 시퀀스·target 매핑 구현
3. 액션별 상태값(before/after) 채우기 로직 구현
4. 추천 후보 1회 선택 보장 + `verify_checkin` 고정 구현
5. 금지 액션 검증 + 고정 필드(`SIMULATION_ONLY` 등) 세팅

병원 환경 화면 흐름 (그대로 따라가면 됨):
```
WELCOME --start--> VISIT_TYPE
VISIT_TYPE --select_visit_type--> APPOINTMENT_CHECK
APPOINTMENT_CHECK --check_appointment--> DEPARTMENT_SELECTION
DEPARTMENT_SELECTION --select_department--> DEPARTMENT_SELECTION
DEPARTMENT_SELECTION --select_flow--> ACCESSIBILITY_SUPPORT
ACCESSIBILITY_SUPPORT --select_support--> CHECKIN_REVIEW
CHECKIN_REVIEW --verify_checkin--> CHECKIN_REVIEW   (마지막 액션, readOnly)
```

### 4단계 — Simulation API 연동
9개 함수가 다 끝나야 시작하는 게 아니라, `buildSubmission()` 뼈대가 잡히면 바로 병행 가능. `examples/minimal-participant-client` 코드 그대로 참고. (위 "비동기 폴링 패턴" 필요)

1. 세션 생성 API 연동 구현 (`POST /api/v1/sessions`)
2. 제출 API 연동 구현 (`POST /api/v1/sessions/:id/submission`)
3. 검증 트리거 + 상태 폴링 로직 구현 (`POST .../validate`, `GET /api/v1/sessions/:id`)
4. Evidence 조회 + 오류코드 파싱 로직 구현 (`GET .../evidence`)
5. API base URL 등 설정 분리 (`config.ts`)

### 5단계 — 통합 & 검증 (전원)
```bash
npm run participant:progress -- --team LEEKIMIMJUNG    # 9/9 확인
npm run participant:validate -- --file <출력파일> --execute   # SIMULATION PASS 목표
```
