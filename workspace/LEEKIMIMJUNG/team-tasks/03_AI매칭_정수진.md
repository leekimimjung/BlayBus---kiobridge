## STEP 4 — `filterCandidates()` (172~208행)

### 목적
`hardConstraints` 위반 후보를 후보군에서 완전히 제거 (점수 깎기 아님, 제거).

### 반드시
- `available === false`인 후보 제외
- 제외 사유 기록해두기 (STEP 6 설명에 사용)

### 절대 금지
- hardConstraint 위반 후보를 낮은 점수로만 처리하고 남겨두기
- `UNKNOWN`인 제약을 "없는 것"으로 간주

### 의사코드
```ts
return candidates.filter((c) => c.available && !violatesHardConstraints(c, ctx));
```

## STEP 5 — `recommend()` (210~247행)

### 목적
남은 후보 순위를 정하고 1순위를 고름. **가중치·점수 설계는 전적으로 우리 몫, 심사 대상.**

### 반드시
- 확신 낮으면 `requiresReconfirmation: true`
- 사용자 사실(`facts`)과 충돌하지 않는 후보를 고를 것

### 절대 금지
- 사용자가 `UNKNOWN`이라고 한 값을 임의로 정해서 고르기
- **증상으로 진료과 추론**

## STEP 6 — `explainRecommendation()` (249~282행)

### 목적
왜 이걸 추천했는지 사람이 읽을 문장으로 설명. **최소 1개 필수** (진행검사에서 확인함).

### 반드시
- 사용한 사용자 정보를 밝힐 것
- 제외한 조건도 설명할 것

### 절대 금지 (이런 문장은 설명이 아님)
"AI가 추천했습니다" / "최적의 선택입니다" / "시스템 판단입니다"

### 좋은 예시
- "포장을 선호하셔서 포장 가능한 메뉴를 먼저 보여드렸습니다."
- "예약 없이 오신 초진이시고 진료과를 직접 말씀하지 않으셔서, 진료과를 임의로 정하지 않고 일반 안내 경로로 접수를 도와드립니다."

## STEP 7 — `buildAlternatives()` (284~311행)

### 목적
1순위가 사용자 뜻과 다를 때 돌아갈 대안 후보 ID 목록.

### 반드시
- 대안도 hardConstraints를 지킬 것

### 절대 금지
- 제외된(hardConstraint 위반) 후보를 대안으로 되살리기

## 병원 후보(candidates) 6개 — 실제 fixture 데이터

| ID | 이름 | 방문유형 | 예약 | 진료과 |

## 매칭 로직으로 처리해야 할 5개 시나리오 (하드코딩/페르소나별 if문 금지!)

같은 매칭 엔진이 `facts`/`preferences`/`hardConstraints` 조건 조합만으로 다른 결과를 내야 합니다.

1. 시각장애 아동 — 초진, 예약없음, 음성안내, 보호자없음 → 안전장치(직원호출) 필수 → **HOS-006으로 유도되거나 STAFF_HELP 필수 지원**
2. 청각장애 환자 — 초진, 예약없음, 청각지원 → 화면 시각 알림으로 대체
3. 재진 고령자 — 재진, 예약있음, 큰글씨 → **HOS-001**, 완료 후 세션 리셋(이건 프론트 담당)
4. 무릎통증 학생 — 초진, 예약없음 → **진료과는 사용자가 직접 선택한 값만 사용** (departmentId가 `UNSPECIFIED`거나 `UNKNOWN`이면 → **HOS-003** 또는 재확인, 자동매칭 금지)
5. (자유 창의) 공황장애 환자 — 재진, "천천히 진행 모드" → 이건 대부분 프론트/UX 몫이지만, 추천 이유 문구에 "천천히 진행" 관련 안내 포함 가능
